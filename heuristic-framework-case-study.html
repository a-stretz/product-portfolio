Overview

A computer vision platform analyzing human movement needed an evaluation layer that could tell a user whether their technique was good — not just detect where their joints were. That layer existed, but it was built entirely around one expert's hardcoded interpretation of "correct" technique.

This is the knowledge-engineering half of a two-part story. Case 01 built the QA system that first proved the platform's outputs could be measured — and in doing so, exposed structural cracks in the heuristic logic underneath them. This case is the rebuild: extracting what expert coaches actually knew, and re-encoding it as a framework instead of a single person's opinion.

01 · Problem

One expert, hardcoded, and un-auditable.

The evaluation system relied on a single expert's interpretation of optimal technique, encoded directly into the model logic. Nobody else, on the team or among users, could see how a given evaluation had been produced, or why.

  • No adaptability across different users, skill levels, or sports
  • Incomplete or incorrect translation of what the expert actually meant
  • No transparency in how any individual evaluation was generated
  • No scalable path to a second sport, let alone a tenth

These weren't hypothetical risks. They were the same weaknesses Case 01's validation pipeline had already surfaced as a source of unreliable output. Fixing the evaluation logic meant going back to where it originated: a single expert's head.

02 · Approach

Two threads, one framework.

Fixing hardcoded, single-source logic meant solving two different problems at once: getting the knowledge out of experts' heads in a usable form, and building an architecture that could actually hold it once extracted.

Thread 01 · Knowledge Extraction

Seven interviews, one structured method

Conducted seven structured extraction interviews with coaching experts, converting tacit movement evaluation, the kind of judgment a coach can demonstrate but rarely articulate in rules, into measurable heuristics with defined tolerances, edge-case exceptions, quality thresholds, and explicit measurement rationale.

Research and multiple expert perspectives were incorporated deliberately, so the resulting logic reflected a documented consensus rather than a single coach's personal style.

Output 7 SME interviews, each yielding tolerances, edge cases, quality thresholds, and the reasoning behind them, not just a pass/fail rule.
Thread 02 · Framework & Metric Architecture

The Heuristic Framework, and the inventory behind it

Wrote the platform's Heuristic Framework and README: the universal measurement architecture mapping extracted ML data into structured evaluation logic and scalable, human-readable feedback rules. Built as a reusable template, configurable per sport, skill level, and user profile, rather than a fixed rule set.

Expanded the Master Metric Inventory from 12 to 33 available metrics, broadening coverage across stance, balance, sequencing, release mechanics, body alignment, and follow-through.

Output 12 → 33 metrics, a 175% increase, documented in a framework any engineer or reviewer could read without the original expert in the room.
The goal was never to make the model smarter. It was to make one expert's judgment legible enough that thirty-three metrics, several sports, and reviewers who had never met that expert could all trust the same evaluation logic.
03 · Key Decisions

Six decisions that made the knowledge portable.

Decision 01

Extraction Before Translation

Each interview separated what the expert meant from how it had previously been implemented, so mistranslations baked into the old hardcoded model didn't carry forward unexamined.

Decision 02

Research + Multiple Experts, Not One

Deliberately incorporated research and more than one expert's perspective, eliminating the single-source dependency that made the original logic un-auditable in the first place.

Decision 03

Configurable Over Fixed

Evaluation criteria became configurable components, tunable per sport, skill level, and user profile, rather than fixed rules requiring a code change for every variation.

Decision 04

Customer Profiles, Not Custom Engineering

Complex evaluation logic was converted into configurable customer profiles, enabling tailored client implementations without touching core platform architecture per customer.

Decision 05

Designed for Interpretability

The framework was written so both technical and non-technical stakeholders could read, question, and audit the evaluation logic, not just the engineers who built it.

Decision 06

Separate Knowledge From Implementation

Domain knowledge was decoupled from code, so expert reasoning could be updated as the framework matured without requiring an engineering change every time.

04 · Impact

From one-time build to persistent capability.

Resolved

  • Replaced hardcoded, single-expert logic with a documented, modular framework
  • Corrected the structural flaws in evaluation logic that Case 01's QA pipeline had exposed
  • Enabled configurable evaluation across users, skill levels, and contexts without new development per variation

Extended

  • Created a scalable foundation for multi-sport motion analysis beyond the original use case
  • Customer profiles allow tailored client implementations without per-customer engineering work
  • Turned expert knowledge into a persistent, auditable, extendable capability instead of a one-time implementation
