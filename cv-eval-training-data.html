Training Data & Annotation Design

Redesigning the annotation requirements for a markerless computer-vision product after recognizing the ML system needed additional, more precisely defined training signals to improve detection and downstream evaluation.

00

Why It Mattered

This was not primarily a data-cleaning exercise. The central product question was: what new information is worth creating, how should it be represented, and how do we make it consistent enough for the model to learn from?

The existing annotation workflow was already reasonably mature — action boundaries, multiple phases, object detection, background examples, basic edge-case handling, and structured temporal output. But the model and evaluation stack had evolved. Downstream logic increasingly depended on knowing the correct person, object, side of the body, spatial relationships, and temporal context.

The need was not "label more data." It was add the right information.

01

My Role

I owned the revisions in the later annotation specification. The process was collaborative: ML and Data Science helped determine which datapoints could improve model behavior, AI engineering helped validate how those outputs would be consumed, and annotation specialists helped determine what could be labeled consistently and at reasonable cost. I translated those needs into the working specification, facilitated decisions, and maintained the executable requirement set.

I did not personally annotate the full dataset or train the production models.
02

System Context

Annotation requirements sit at an unusual interface — understandable to humans while producing data that's useful to models. The work mattered because the downstream product depended on these outputs for event timing and asymmetric evaluation.

03

The Design Problem

A label can fail in at least four ways. The revision addressed all four.

Failure mode

Semantically wrong

It does not represent what the model actually needs.

Failure mode

Ambiguous

Two annotators could reasonably apply it differently.

Failure mode

Operationally expensive

The incremental model value doesn't justify the annotation effort.

Failure mode

Temporally misleading

Technically true for the action but not observable in every frame.

Cross-functional decision example. One proposed object-keypoint task could have expanded into a very large annotation effort. Instead, the discussion focused on three questions: what downstream capability will actually consume these keypoints, how many examples are likely sufficient to test the hypothesis, and how do we sample across viewpoints and conditions rather than overrepresent one source. That moved the conversation from annotation completeness to experimental value per annotation dollar.

Sanitized Requirement Pattern

A public-safe representation of the kind of requirement structure introduced — illustrative only, not the production schema.

Illustrative only — does not reproduce the production schema or proprietary class/field names.

annotation_class: target: definition: "the object/person used by downstream evaluation" identity_rule: "maintain identity across the action" occlusion: partial: "continue when location remains inferable" full: "resume same identity when confidence supports continuity" attributes: execution_side: values: [primary_side_a, primary_side_b] ambiguity_note: "may not be visually learnable in every frame" edge_cases: - multiple_candidates - motion_blur - perspective_change - atypical_form qa: report_ambiguities: true
06

Validation

The ML team used the revised data as part of subsequent model changes and QA. This work contributed to the broader model-improvement initiative alongside temporal-boundary logic, model changes, measurement formula revisions, and QA improvements.

07

Outcome

The revised training-data design was a significant contributor to the broader model-improvement initiative.

  • Model-relevant object definitions replaced broader visual classes
  • Deterministic person-of-interest rules removed a source of annotator disagreement
  • New attributes and spatial datapoints were added only where a clear downstream use justified the cost
  • Difficult-scene requirements (occlusion, blur, perspective) became explicit rather than implicit
08

Limits & Attribution

I owned the specification and facilitated the cross-functional decisions behind it. I did not personally annotate the dataset, and the selection of which new model datapoints were worth adding was collaborative with ML and Data Science — not something I determined independently.
