Case Study 05 · BMCD Bracket Pool Analyzer

Exact probability at the margins of elimination.

Overview

A 21-person NCAA Tournament bracket pool hosted on CBS Sports, running through the 2026 March Madness tournament. Bracket data lived entirely inside CBS Sports' web platform — no API, no CSV export, no structured data access. Individual bracket PDFs were the only extractable format, each containing a visual bracket tree with color-coded correct and incorrect picks overlaid on top of predicted picks.

The pool used a non-standard scoring model (round-weighted base points plus winning seed as a bonus), so no off-the-shelf bracket analytics tool could score it correctly. The tool needed to work during an active tournament with games happening that night — the initial build had to go from zero to functional in a single working session, and the architecture had to support rapid state updates across multiple rounds.

01 · Problem

"Can I still win?" — a surprisingly deep question.

Bracket pools generate a question every participant asks but almost nobody can actually answer. The real version of that question has surprising depth: not just who's ahead in points, but which future game outcomes help which participants, which combinations of outcomes eliminate someone mathematically, how much a dead champion pick compresses someone's ceiling, and which participants are alive at 3% versus truly at zero.

Combinatorial space
For a 21-person pool with 11 remaining games at the Sweet 16 stage, there are 2,048 valid tournament paths. No one in the pool could do this math, and no consumer bracket tool on the market answers it — ESPN, CBS, Yahoo, and others show current standings but don't model forward probability.

The secondary problem was data extraction. CBS Sports provides bracket data as visual PDFs with overlaid annotations, not structured data. Building any analytical tool required first solving the parsing problem — extracting 21 participants' picks across 63 games each from semi-structured visual documents, including edge cases like participants who picked teams that were eliminated before their predicted game even occurred.

02 · Approach

Seven engineered layers on top of a parsed dataset.

Layer 01 · Data Extraction

Parsing CBS Sports PDFs into structured picks

Bracket PDFs were uploaded and parsed using visual inspection of the CBS Sports format. Each contained two layers of information: the participant's predicted winner (positioned on the bracket line) and the actual result (overlaid in green for correct, red with strikethrough for incorrect).

These had to be decoded into structured pick objects mapping each participant's predicted winner for every round — including edge cases like participants who picked teams eliminated before their predicted game occurred, resulting in null picks for downstream slots.

Volume 21 participants × 63 games = 1,323 pick data points, manually cross-validated.
Layer 02 · Scoring Engine

Custom pool rules as a scoreGain() function

The pool's scoring model: base points by round (1 / 2 / 4 / 8 / 16 / 32) plus the winning team's seed number as a bonus on every correct pick. A 9-seed winning in the Elite Eight earns 17 points (8 base + 9 seed).

This creates asymmetric value — upset picks carry disproportionate reward, a deliberate design choice in the pool's scoring that the probability engine needed to respect throughout.

Layer 03 · Probability Engine

Exhaustive enumeration, not Monte Carlo

The architecture decision that defines this project. Rather than sampling random tournament outcomes, the engine enumerates every valid combination of remaining game results. At the Sweet 16 with 11 remaining games, this is 2,048 scenarios.

Each scenario is assigned a probability computed as the product of per-game win probabilities. Direct matchups use betting-line-derived probabilities; conditional matchups use a head-to-head rating model calibrated from betting markets.

Why exhaustive Monte Carlo at 100K iterations can report 0% for someone with 0.02% true probability. Exhaustive enumeration gives exact answers — the difference between "eliminated" and "extremely unlikely".
Layer 04 · Conditional Resolution

Constraint propagation over a tournament DAG

A dependency cascade handles the fact that later-round matchups depend on earlier-round outcomes. When a user locks in a Sweet 16 result, deriveConditional() propagates that outcome forward — invalidating downstream picks that become impossible and unlocking new matchups whose participants are now determined.

Essentially a constraint propagation engine running on a directed acyclic graph of tournament dependencies.

Layer 05 · Rank Computation

Exact finish distributions, not point projections

For each of the 2,048 scenarios, all 21 participants are scored, sorted by total points with tiebreaker logic (predetermined tiebreaker number from CBS), and assigned ranks.

Win probability is the sum of scenario probabilities where a participant finishes 1st. Top-2 and top-3 probabilities sum across scenarios where they finish ≤ 2nd or ≤ 3rd respectively. This produces exact pool finish distributions, not approximations.

Layer 06 · Interactive Bracket UI

Athletic-style visualization with live recompute

Absolutely-positioned game cards on a fixed canvas, connected by L-shaped SVG connector lines. Each connector segment is color-coded by the leading team at that bracket position, with opacity scaled by win probability and percentage labels floating above the output line segment.

Game cards are clickable — locking a result triggers conditional resolution → scenario enumeration → probability recalc → SVG re-render → standings re-sort, all in a single synchronous pass.

Layer 07 · Modal Analysis

Participant-level "what needs to happen for me to win"

Clicking any participant's name opens a detailed breakdown: win / top-2 / top-3 probabilities, their most probable winning path (the highest-probability scenario where they finish 1st) with per-game results and checkmarks where their picks align, the runner-up and margin in that scenario, and a required outcomes panel showing which game results appear in ≥ 62% of their winning scenarios — surfacing the critical dependencies for their path to victory.

This is the core product insight: raw standings and win percentages tell you what the situation is, but not why or what needs to happen. The modal bridges that gap — showing a specific participant that Iowa State must win tonight, Arizona must beat Purdue Saturday, and Iowa State must then beat Arizona in the Final Four. That's the conversation bracket pool participants actually want to have.

Exactness matters at the margins. Monte Carlo sampling, even at 100K iterations, can report 0% for a participant who actually has a 0.02% chance. The difference between "eliminated" and "extremely unlikely" is the difference between "you can stop watching" and "you need a miracle but it exists."
03 · Key Decisions

Architecture choices optimized for iteration speed and analytical rigor.

Decision 01

Single-File Architecture

The entire application — data, logic, UI, and styles — ships as one HTML file. No server, no build step, no dependencies beyond Google Fonts. Drag to Netlify Drop, share the URL in 30 seconds.

Decision 02

Exhaustive Over Monte Carlo

At small scenario counts (≤ ~10K), exhaustive enumeration produces better answers with less code. Monte Carlo is only justified when the scenario space is too large to enumerate — which it isn't until early rounds.

Decision 03

Pre-Locked Completed Games

Completed results are hardcoded into outcome state. This avoids retroactive scoring complexity and keeps the enumeration space small. The tradeoff: manual version updates. The benefit: the engine enumerates only over remaining uncertainty.

Decision 04

Rating-Based Conditional Odds

For matchups where participants aren't yet known, win probability uses a relative-strength rating model rather than fixed odds. Conditional probabilities automatically adjust when earlier games lock — no separate odds table per matchup permutation.

Decision 05

Best-Case Modal Per Participant

Raw standings tell you what; the modal tells you what needs to happen. Showing a specific participant's required outcome set is the conversation bracket pool participants actually want to have.

Decision 06

Alert Banner for Pool Dynamics

When the Final Four was set and neither UConn nor Illinois had any champion pickers, the tool surfaced it as a top-level alert. This "so what" interpretation layered on top of raw data is where analytics tools differentiate.

06 · Skills Demonstrated

What the build exercises.

Capability 01

Probability & combinatorics

Exhaustive scenario enumeration with weighted probability trees. Product-of-conditionals probability across a dependency DAG. Head-to-head rating model for conditional matchup resolution. Exact rank distribution computation across all valid tournament paths.

Capability 02

Data extraction & structuring

Parsing semi-structured visual bracket PDFs into normalized data objects. Handling annotation layers (correct / incorrect overlays), edge cases (null picks from pre-eliminated teams), and manual cross-validation of 1,323 individual pick data points.

Capability 03

Constraint propagation

Conditional game resolution as a dependency cascade — locking an upstream outcome invalidates impossible downstream states and enables new matchups. Analogous to constraint satisfaction problems in scheduling and configuration systems.

Capability 04

Frontend engineering

SVG-based data visualization with programmatic geometry computation — connector line positioning, center-Y calculations, team-color-coded segments. Absolute-positioned layout on a fixed canvas. Single-file architecture with no framework or build step.

Capability 05

Product analytics framing

Scoring model, probability engine, and UI all serve a product question (can I still win?) rather than a mathematical abstraction. The modal shows the specific path to victory, critical dependencies, and margin in the best-case scenario. The alert banner interprets structural dynamics into strategic insight.

Capability 06

Rapid iteration under pressure

Five versions across a live tournament with games happening during the build. Each version added meaningful capability while maintaining correctness of the underlying probability engine. Architecture decisions optimized for iteration speed without sacrificing analytical rigor.

◆   Final Summary

A real-time probability engine that answers the question every bracket-pool participant asks but no consumer tool solves.

The tool correctly identifies mathematical eliminations, computes exact win probabilities to the tenth of a percent, handles edge cases like null picks and pre-eliminated champion selections, and provides per-participant tactical analysis. It runs entirely client-side with no backend, loads in under 200 ms, and deploys via drag-and-drop to a static hosting service.

This project demonstrates probability modeling, combinatorics, constraint propagation, SVG data visualization, single-file architecture, and rapid product iteration under live-event time pressure.
