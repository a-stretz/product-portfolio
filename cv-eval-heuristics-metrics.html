00

Why It Mattered

The product transformed pose and object data into coaching evaluation. That sounds like a simple pipeline — keypoints → measurement → score — but every metric carried hidden assumptions.

A metric could be wrong because the wrong landmarks were used, a derived point didn't represent the intended physical concept, an input was too unreliable under occlusion, a formula measured a proxy rather than the intended behavior, the metric ran across the wrong phase window, or the scoring range didn't match the coaching meaning. "The code runs" was not a sufficient acceptance criterion.

01

My Role

I reviewed the evaluation logic from the product/domain side and owned multiple revisions to the Heuristics & Metrics specification — identifying outdated assumptions, comparing documented formulas with implemented formulas, flagging risky or unreliable landmark inputs, redefining metric timing, and documenting the intended physical meaning so future contributors could understand why the implementation existed.

I collaborated with technical contributors to validate feasibility and implementation. I did not claim ownership of every engine feature or every code revision.
02

System Context — Making Expertise Executable

This workstream sits on top of an earlier one: turning one expert's coaching judgment into structured, auditable logic. Statements like "the hand should be vertical" or "measure the athlete at the set point" are understandable to a coach but insufficient for an automated system. Making that translation legible and reviewable end to end was the core of this work:

Coaching Expertise
→
Machine-Observable Signals
→
Measurable Geometry / Timing
→
Scoring Behavior
→
User Interpretation

Domain intent had to survive translation into explicit landmarks, geometric relationships, event boundaries, measurement formulas, timing windows, aggregation behavior, scoring rules, and edge-case behavior — without losing what the coach originally meant.

03

Expected → Actual → Proposed

For each metric, I compared the intended coaching/biomechanical purpose (Expected) against what the implemented code was actually calculating (Actual), then proposed a corrected approach using reliable inputs (Proposed). This caught semantic defects — cases where a formula was technically valid and still wrong for the product because it used unreliable landmarks, measured a proxy rather than the intended behavior, or ran at the wrong point in the movement.

Expected

Intended behavior

Measure body alignment using reliable landmarks at the critical event window.

Actual

Implemented behavior

Measurement depends on fragile / indirect inputs and broad timing.

Proposed

Corrected approach

Simpler landmarks + a player-relative reference + an explicit event window.

The repeated pattern: prefer the simplest reliable measurement that preserves the intended meaning.

04

Timing Was Part of the Metric Definition

Earlier configuration often attached many metrics to broad phase ranges. The mature model separated what should be measured from when it should be measured, defining each metric as single-frame, continuous-window, frame-average, ratio/percentage, or duration between events. The specification also moved toward neutral Primary/Support terminology instead of hard-coding one sport's left/right language — making asymmetric logic easier to reason about and reusable across activities. I contributed to these input and naming revisions; I do not claim sole ownership of the broader multi-activity architecture.

06

Validation

Metric validation depended on isolating timing from formula correctness — using known-good frame ranges to ask whether, given the correct physical moment, a formula produced a measurement consistent with intended coaching behavior. This work contributed to the broader model-improvement initiative alongside training-data, temporal-boundary, model, and QA changes, and connected directly into the program's broader QA strategy.

07

Outcome

The evaluation layer became more explicit and auditable — reducing the risk of technically valid but semantically incorrect evaluation.

  • Each metric's meaning, inputs, timing, aggregation, and scoring became explicit and documented
  • Configuration became a contract between Product, domain expertise, Data Science, and engineering
  • Terminology moved toward reusable, activity-scoped concepts instead of single-sport language
  • Future contributors could understand not just what number to compute, but why the metric existed
