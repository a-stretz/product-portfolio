Temporal Detection & Event Boundaries

Helping redefine how a computer-vision motion-analysis system identified meaningful event boundaries — because downstream metrics depended on exactly which frame or frame window represented the intended biomechanical event.

00

Why It Mattered

The problem was not simply detecting an action. The evaluation engine was phase-aware — a joint angle measured too early or too late could be mathematically correct for that frame and still wrong for the evaluation.

The dependency ran: event detection → frame selection → keypoint state → metric value → score → user feedback. A late boundary could propagate into an inaccurate evaluation even when every downstream formula executed correctly. That made temporal detection part of the product's measurement system, not just an ML classification problem.

01

My Role

I worked on the product-side definition of event boundaries and their relationship to downstream measurement, turning domain descriptions of movement into observable events that ML/engineering teams could detect consistently. I also tracked a later shot-detection delay related to post-processing state logic and helped structure validation so downstream heuristics could keep being tested while that upstream issue was investigated.

I did not write the production state machine or LSTM implementation.

04

Isolating Timing From Measurement

Later in the program, the team identified a delay in action detection. The suspected cause was not necessarily the trained model itself — the investigation focused on post-processing/state-machine behavior. From a product perspective this was high priority because timing affected metric frame selection, scoring, visible overlays, and the credibility of user feedback. But waiting for the full detection investigation to conclude would have blocked evaluation work.

I proposed continuing heuristic validation using controlled, known-good frame ranges — asking a narrower question: if we provide the correct action, phase, and metric timing manually, do the metric outputs reflect their intended purpose? That separated two hypotheses: the detector is choosing the wrong frame, versus the metric is wrong even given the correct frame. This let debugging continue in parallel instead of treating the entire inference-to-score chain as one black box.

I helped structure the investigation and created a controlled-input path so downstream metric QA could continue while the timing defect was investigated. I did not fix the production state machine.

06

Validation

The temporal work provided a more rigorous interface between activity recognition and the measurement engine, and directly informed the later metric redesign — where some metrics moved from broad phase ranges to a specific event frame, a deliberate interval between two events, or continuous measurement within a constrained window. This work contributed to the broader model-improvement initiative alongside training-data, measurement, model, and QA changes.

07

Outcome

Event boundaries stopped being treated as metadata and became explicit measurement gates.

  • Boundary criteria became objective, technique-reliable, and detectable — not coaching language a model can't observe
  • Primary/confirmation/backup/fail-safe logic replaced single fragile triggers
  • A controlled-input testing path let metric validation and detector debugging proceed independently
  • Metric timing moved from broad phase windows toward metric-specific event windows
08

Limits & Attribution

I defined boundary requirements at the product level and designed the controlled-input validation strategy. I did not write the production state machine or LSTM implementation, and I don't claim to have personally resolved the underlying detection-timing defect.
